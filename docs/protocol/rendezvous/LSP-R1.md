## 1. Overview & Architecture

LSP-R1 defines a zero-marginal-cost ($0), privacy-preserving rendezvous and presence protocol for paired LibreShare devices across network boundaries. It operates over public Nostr relays (NIP-01) with optional ntfy.sh fallback.

Rendezvous is **not a file transport**; it acts exclusively as an out-of-band **candidate and offer signaling source** feeding into LibreShare's connection manager (`ConnectionManager`). All file transfers occur over direct TLS paths (Increment 5b) or end-to-end encrypted tunnels (Increment 5).

```
+--------------------+                 +---------------------+
| Device A (Sender)  |                 | Device B (Receiver) |
+---------+----------+                 +----------+----------+
          |                                       |
          | 1. Presence (Encrypted Envelope)      |
          +--------------> [ Nostr Relay ] <------+ (Subscribes to Channel)
          |                                       |
          | 2. Offer (Encrypted Envelope)         |
          +--------------> [ Nostr Relay ] ------>+
          |                                       | (Prompts User for Consent)
          | 3. Reply (Encrypted Accept/Reject)    |
          +<-------------- [ Nostr Relay ] <------+
          |                                       |
          | 4. Data Transfer (Direct TLS / Tunnel)|
          +=======================================>+
```

## 2. Cryptographic Keys & Channel Derivation

### 2.1 Pairing Secret (`K_pair`)
Pairing derives a mutual 256-bit symmetric key $K_\text{pair}$ stored securely in each device's `SecretStore` under the key `pair:<deviceId>`.

- **Invite Secret ($S$):** 32 cryptographically secure random bytes generated by the inviter, valid for 10 minutes.
- **Invite URI:**
  ```text
  libreshare://pair?v=1&s=<base64url(S)>&fp=<inviter_fp_hex>&alias=<alias>
  ```
- **Key Derivation:**
  Given inviter nonce $n_A$ (16 bytes), scanner nonce $n_B$ (16 bytes), and normalized 64-hex SHA-256 certificate fingerprints $fp_A, fp_B$:
  $$\text{order}(fp_A, fp_B) = (\min(fp_A, fp_B), \max(fp_A, fp_B))$$
  $$K_\text{pair} = \text{HKDF-SHA256}(\text{ikm}=S, \text{salt}=n_A \parallel n_B, \text{info}=\text{"LSP-R1 pair"} \parallel \min(fp) \parallel \max(fp), L=32)$$

### 2.2 Ephemeral Channel Rotation
To prevent metadata linkage and traffic analysis by relay operators, communication channels rotate daily using 24-hour UTC epochs:
$$E = \lfloor \text{unix\_timestamp\_seconds} / 86400 \rfloor$$

1. **Channel Identifier ($C_E$):**
   $$C_E = \text{hex}(\text{HMAC-SHA256}(K_\text{pair}, \text{"LSP-R1-CHAN"} \parallel \text{uint64\_be}(E) \parallel \text{peer\_deviceId}))$$
   The channel identifier is a 64-character hex string used as the Nostr subscription tag.

2. **Envelope Encryption Key ($K_\text{env}$):**
   $$K_\text{env} = \text{HKDF-SHA256}(K_\text{pair}, \text{salt}=\text{uint64\_be}(E), \text{info}=\text{"LSP-R1-ENV"}, L=32)$$

3. **Midnight Grace Window:**
   Clients subscribe to channels for both epoch $E$ and epoch $E-1$ within a 120-second boundary around 00:00:00 UTC to prevent dropped signaling during transition.

## 3. Nostr Envelope Framing (NIP-01)

Rendezvous envelopes are published as ephemeral Nostr events (Kind 20000..29999 or Kind 1059 Gift Wrap):

```json
{
  "kind": 20059,
  "pubkey": "<ephemeral_bip340_pubkey_hex>",
  "created_at": <unix_seconds>,
  "tags": [
    ["p", "<channel_id_hex>"],
    ["expiration", "<unix_seconds_plus_ttl>"]
  ],
  "content": "<base64url(payload)>",
  "id": "<sha256_of_serialized_event>",
  "sig": "<bip340_schnorr_signature>"
}
```

### 3.1 Content Encryption & Length Bucketing
The `content` field is an AES-256-GCM ciphertext protecting the inner JSON record:
- **Cipher:** AES-256-GCM with 96-bit random IV and 128-bit authentication tag.
- **AAD:** ASCII string `"LSP-R1:"` followed by `channel_id_hex`.
- **Length Bucketing:** Before encryption, plaintexts are padded to discrete bucket boundaries (512, 1024, 2048, or 4096 bytes) using zero bytes with a 2-byte big-endian prefix specifying payload length:
  $$\text{plaintext} = \text{uint16\_be}(\text{len}) \parallel \text{json\_bytes} \parallel \text{padding}$$
  This prevents relay operators from distinguishing between presence pings, probes, and transfer offers by payload length.
- **Encoded Output:** `base64url(12-byte IV || ciphertext || 16-byte MAC)`.

## 4. Record Schemas

Inner decrypted records are JSON objects conforming to `schemas/rendezvous-record.schema.json`. Every record carries common headers:
- `v`: Protocol version integer (`1`).
- `type`: Record discriminator string.
- `seq`: Monotonically increasing 64-bit integer per sender/channel.
- `issuedAt`: Unix timestamp in milliseconds.

### 4.1 `presence` Record
Emitted periodically (every 3–5 minutes) when Receive mode is active.
```json
{
  "v": 1,
  "type": "presence",
  "seq": 104,
  "issuedAt": 1799284800000,
  "ttl": 300,
  "candidates": [
    {
      "kind": "directIpv6",
      "host": "2001:db8::1",
      "port": 53330
    },
    {
      "kind": "mappedIpv4",
      "host": "198.51.100.1",
      "port": 53330
    }
  ],
  "caps": ["rdv1", "tls13"]
}
```

### 4.2 `probe` Record
Used to measure round-trip latency to a peer without initiating a transfer.
```json
{
  "v": 1,
  "type": "probe",
  "seq": 105,
  "issuedAt": 1799284805000,
  "nonce": "k2m8Xq9p..."
}
```

### 4.3 `offer` Record
Initiates a transfer session across network boundaries.
```json
{
  "v": 1,
  "type": "offer",
  "offerId": "off_9f82bc710a",
  "seq": 106,
  "issuedAt": 1799284810000,
  "manifest": {
    "sessionId": "ses_4a11b8",
    "totalSize": 104857600,
    "files": [
      { "name": "project.zip", "size": 104857600, "sha256": "3a9f..." }
    ]
  },
  "tunnelOffer": {
    "provider": "cloudflare",
    "url": "https://quick-tunnel.example.com",
    "token": "t_abc123"
  },
  "candidates": [
    {
      "kind": "directIpv6",
      "host": "2001:db8::1",
      "port": 53330
    }
  ]
}
```

### 4.4 `reply` Record
Receiver's response to an `offer`. Contains a cryptographically sealed acceptance or rejection token.
```json
{
  "v": 1,
  "type": "reply",
  "offerId": "off_9f82bc710a",
  "seq": 42,
  "issuedAt": 1799284812000,
  "decision": "accept",
  "sealedAck": "base64url_hmac_of_decision"
}
```

### 4.5 `revoke` Record
Permanently revokes pairing status between devices.
```json
{
  "v": 1,
  "type": "revoke",
  "seq": 107,
  "issuedAt": 1799284820000,
  "revokedAt": 1799284820000
}
```

## 5. Security & Privacy Rules

1. **No Auto-Accept (R7):** Rendezvous offers MUST never be auto-accepted, even from trusted contacts. Every transfer offer requires explicit interactive user confirmation.
2. **Replay Rejection:**
   - Records with timestamp skew $| \text{currentTime} - \text{issuedAt} | > 120 \text{ s}$ MUST be dropped.
   - Any message where `seq <= highest_seen_seq` for that peer MUST be dropped.
3. **Secret Hygiene:**
   - Implementations MUST NOT log, print, or trace $S$, $K_\text{pair}$, $K_\text{env}$, decrypted envelope contents, or candidate IPs.
4. **Relay Decoupling:**
   - Relays are untrusted third parties. If a relay tampers with or withholds events, the client detects it via sequence gaps or signature verification and immediately falls back to alternate relays.
