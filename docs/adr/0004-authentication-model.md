# ADR 0004: Authenticate the sender with a signed per-request proof over TLS 1.3 with a pinned server, not with TLS client certificates

- Status: accepted (docs/plans/inc3.md question Q1: amendment proposed to the user, no veto, accepted by the orchestrator on 2026-11-04)
- Date: 2026-11-04
- Spec: `docs/LIBRESHARE_BUILD_SPEC.md` sections 4.6 and 5 (FR-05, FR-16, NFR-04); `docs/plans/inc3.md` findings 1, 3, 4, 5 and decisions D1, D2, D3, D7, D8, D9, D10
- Protocol: `docs/protocol/LSP-1.md` sections 0.3, 4.3.6, 4.7 and 5; schemas `auth-proof`, `session-request`, `discovery-announce`
- Amends: spec section 5 and LSP-1 section 5, which said "mutual TLS: server `requestClientCertificate: true`" (FR-05 "mutual TLS" becomes "mutual authentication over TLS 1.3")
- Related: ADR 0001 (pure-Dart core), ADR 0005 (SAS commit/reveal)

## Context

FR-05 asks for mutually authenticated, fingerprint-pinned connections between two devices that have never met: no certificate authority, no account, self-signed certificates, trust on first use confirmed by a short authentication string (SAS).

With `dart:io` that cannot be built as written. `HttpServer.bindSecure` has `requestClientCertificate` but no `requireClientCertificate` and no bad-certificate hook; `SecureServerSocket.bind` has both flags but still no `onBadCertificate`; the native server code calls `SSL_set_verify(PEER)` with no callback; and the SDK's own client-certificate test makes the server trust the client's authority (`setTrustedCertificates` + `setClientAuthorities`). The conclusion, to be confirmed by spike S-A on the pinned toolchain, is that a stranger's self-signed client certificate fails the handshake, so first contact (TOFU plus SAS) is impossible with TLS client certificates (plan finding 1). A runtime update of the server's trust set per pairing is unverified and only helps peers that already paired.

Other facts that shape the decision: every client in the repository is plain HTTP today (finding 4), so TLS has to arrive as an explicit configuration; the `cryptography` package has no pure-Dart NIST P-256 (finding 3) while `pointycastle` 4.0.0 (MIT, no native code) provides ECDSA; and the same signing primitive is needed later by link manifests (Increment 5), presence records (Increment 6) and BLE authentication (Increment 7), none of which can use TLS client certificates because a tunnel provider terminates TLS.

## Decision

1. **Transport.** TLS 1.3 only. The server certificate is the device identity certificate (self-signed ECDSA P-256, `CN` = deviceId, no subjectAltName, 10-year validity, created once and never re-issued for the same key). The server never requests a client certificate. The client uses `SecurityContext(withTrustedRoots: false)` and decides in `badCertificateCallback`: it compares the SHA-256 of the DER certificate with the pinned fingerprint before any HTTP byte is sent; without a pin it connects, learns the fingerprint and authenticates the server by SAS (ADR 0005). No ALPN, HTTP/1.1, no redirects.
2. **Sender identity.** The sender signs every request that creates a relationship (`POST /sessions`, `POST /register`, `POST /pair`, `POST /sessions/{sid}/sas`, and `GET /info` towards a Contacts-only receiver) with `X-LS-Auth: v1.<cert>.<ts>.<nonce>.<sig>`. The signed text covers method, target, SHA-256 of the body, timestamp, nonce, the server fingerprint the client saw in the handshake, and the client fingerprint. Window +-120 s, nonce cache 5 min / 8192 entries, certificate at most 2 KiB, header at most 4 KiB (LSP-1 4.3.6). Because the signature names the server fingerprint, a relaying man-in-the-middle, which terminates TLS with its own certificate, obtains a proof that the real receiver rejects (channel binding); an impersonating man-in-the-middle with its own identity towards both ends is caught by the SAS or by the pin.
3. **What is pinned.** The fingerprint stays the uppercase hex SHA-256 of the DER certificate (LSP-1 0.2): hashing needs no parsing of attacker-controlled bytes, and the value already flows through announces, mDNS `fp`, `libreshare://peer` links and the peer registry. An SPKI-hash fingerprint was rejected: it would change a published definition and gains nothing while certificates are immutable. A lost key or certificate is surfaced as `IdentityLost`; a new identity is created only by an explicit action, never silently (peers would see KEY_CHANGED).
4. **Certificates in pure Dart.** Own `security/cert_factory.dart` on `pointycastle` (the only new core dependency) with a strict DER reader. Rejected: `basic_utils` (CSR round-trip, heavy transitive dependencies), shelling out to `openssl` (absent on Windows and Android), `cryptography` (no P-256), FFI to BoringSSL (native build burden on three platforms), RSA (slow key generation in Dart).
5. **Signature domains.** One sign/verify helper, with a domain label and a NUL byte in front of every message (`SigDomain`, LSP-1 section 5): `LSP1-AUTH-v1`, `LSP1-SAS-C`, `LSP1-SAS-V`, `LSP1-BYE`, `LSP1-PAIR-REQ`, `LSP1-PAIR-ACK`, and the HKDF info prefix `LSP-R1 pair`. A value made for one purpose never verifies for another, and Increments 5 to 7 reuse the helper with their own labels.
6. **Trust and key changes.** Trust on first use through the SAS; a known `deviceId` that presents another certificate is refused on both sides (`403 KEY_CHANGED` from the receiver, a local `PeerKeyChanged` from the sender) and never auto-accepted, even for a trusted contact. No automatic or cross-signed key rotation (D7): cross-signing only helps planned migration, and the case rotation exists for (a stolen key) is exactly where an old-key signature proves nothing.
7. **Downgrade.** TLS is never negotiated down. A client that requires TLS never retries over HTTP; a peer with an empty fingerprint is "legacy": listed, not selectable, sendable only through an explicit override (CLI `--allow-insecure`); a TLS-only listener answers a plaintext client by closing the connection. An announcement with an empty or different fingerprint never overrides a pinned device. Plain HTTP stays defined as the plaintext profile for loopback and test networks (LSP-1 0.3).
8. **Rejected alternatives for the transport.** (a) True mTLS with pre-trusted client certificates: works only for peers that already paired. (b) A second plaintext "introduction" port: reopens the downgrade surface. (c) A pure-Dart TLS stack or FFI to OpenSSL: unaudited, or three native builds. (d) Protocol sniffing (TLS vs HTTP) on one port: `HttpServer.listenOn` takes a `ServerSocket` and `SecureServerSocket` is not one, so it needs a hand-built socket multiplexer for no gain.

### Deviations from docs/plans/inc3.md, as built

These were decided while the protocol documents were written and are recorded here so that plan, code and `LSP-1.md` can be reconciled.

- **Version.** The plan said `kProtocolVersion = '1.1'`. As built, `kProtocolVersion` stays `'1.0'` for the plaintext profile (two Increment 1 conformance tests pin it and must not be edited), a device in the secure profile reports `'1.1'` (`kProtocolVersionSecure`) in `GET /info`, `SessionRequest.sender`, announces and `bye`, and `kSupportedMajors` stays `['1']`: a peer with any `1.x` is accepted by both profiles.
- **Profile-scoped limits.** The 4 MiB `POST /sessions` cap (D11) and the mandatory `X-LS-Chunk-SHA256` header apply to the secure profile only, because the Increment 1 conformance tests pin 256 KiB (exactly 256 KiB accepted, one byte more is 413) and an optional chunk hash for the plaintext profile. The plaintext profile therefore carries about 1,000 files per session, not 10,000.
- **Signed text.** The plan wrote the signed text as `"LSP1-AUTH-v1\n"` followed by the fields. The signing primitive (`IdentityProvider.sign(domain, message)`) computes `domain + 0x00 + message` for every domain, so the label is followed by NUL and the fields are joined by LF. `docs/protocol/test-vectors-inc3.md` is authoritative.
- **SAS reveal mismatch.** The plan table said "403 AUTH_INVALID"; the error code is 401 (the status of each code is fixed, LSP-1 4.3.5), so a mismatch is 401 AUTH_INVALID.
- **Schema location.** The four new schemas live in `docs/protocol/schemas/lsp11/` because `schema_conformance_test.dart` pins the exact set of nine top-level files and must not be edited. Their `$id` values do not contain the directory, so hoisting them later changes no reference.
- **Pairing confirmation.** The plan names the `PairResponse.mac` without a formula; it is `HMAC-SHA256(S, "LSP1-PAIR-ACK" 0x00 || fpA || fpB || nA || nB)`, a new label next to `LSP1-PAIR-REQ`.

## Consequences

- Positive: first contact works with `dart:io` as it is; no server-side trust-set mutation; the proof is the only authenticator, so even if spike S-A shows that the handshake accepts unknown client certificates nothing changes (`request.certificate` would at most become an extra check). A single signing helper serves five increments, and a stolen TLS session is useless without the key.
- Positive: a relaying man-in-the-middle fails without any human action (server-fingerprint binding), the SAS only has to catch the impersonating one (ADR 0005), and downgrade is impossible by construction.
- Negative: the spec wording "mutual TLS" no longer holds literally; spec section 5, FR-05's text and `docs/traceability.md` are amended ("mutual authentication over TLS 1.3"). Reviewers who expect `requestClientCertificate` need this ADR.
- Negative: the crypto is ours. Strict DER parsing, signature verification of attacker-controlled input and constant-time comparisons are security-sensitive; mitigations are length caps, fuzz tests (10,000 mutated certificates and headers never throw past the boundary), an `openssl` oracle test that skips when `openssl` is absent, and published known-answer vectors.
- Negative: proofs cost a signature per request. Budgets: key generation at most 500 ms, sign at most 50 ms, verify at most 100 ms on a mid-range phone; if exceeded, sign once per session and cache verified proofs.
- Negative: contacts-only stealth is best effort. Probe replies trust an unauthenticated fingerprint claim, so anyone who knows a contact's fingerprint can learn that the device exists; HTTPS stays closed to strangers (404). Signed announcements are a later option.
- Neutral: pairing (LSP-1 5.3) and Contacts-only visibility (5.4) build on the same proof; `K_pair` is derived locally and never travels.
