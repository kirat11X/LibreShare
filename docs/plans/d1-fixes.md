## MUST fix (gate blockers)

| ID | Severity | Problem (one line) | Required behaviour (what the test asserts) |
|---|---|---|---|
| **S1** | BLOCKER | Settings "Save" shows "PIN configured" and clears the field BEFORE the write; the write is an unawaited closure with no try/catch (`settings_screen.dart:604-623`) | Success is shown only after `put('app-pin')` returned AND reading it back equals the digits AND `setPinMode(fixed)` finished. On failure: visible error ("Could not save the PIN. Nothing was changed."), mode unchanged, field kept, no engine rebuild, no unhandled zone error. Button disabled while saving; every `setState` guarded by `mounted`. |
| **S2** | HIGH | Changing the PIN while the mode is already Fixed does not rebuild the engine (`setPinMode` returns early, `settings_provider.dart:59`); the OLD PIN stays enforced until restart | After "Change" + Save the engine's guard enforces the NEW PIN: old PIN gives `pinInvalid`, new PIN passes; stored bytes = new PIN. Mechanism is the coder's choice (a non-secret revision counter the engine watches, or an explicit invalidate after a successful write); the PIN itself must never sit in any provider state that has a `toString`. |
| **S3** | HIGH | The sender's PIN dialog is a `const TextField` with no controller and no submit; `beginSendTo` is never given `pin:` (`transfer_screen.dart:129-171`, `transfers_provider.dart:290-295`). An app sender cannot send to a PIN-protected receiver; demo step 4 cannot work from the phone | Dialog has a controller, a submit button (key `pin-submit`) and `onSubmitted`; validates `^[0-9]{6}$` with a visible message; calls a new `TransfersNotifier.retryWithPin(key, pin)` that starts a new `beginSendTo(device, files, pin: pin)` and replaces the failed view. Correct PIN: files arrive, phase completed. Wrong PIN: text exactly "That PIN was not accepted." with no digits, no attempt count. The PIN lives only in the local controller and the call argument: never in `TransferView`, route params, logs; `toString()` of any view/state has no PIN. Test through the UI with two real engines (not `engine.sendFiles(pin:)`). Also map a `blocked` refusal to a neutral fixed sentence (S13c): "This device is not accepting PINs right now. Try again later." (no counts, no time). |
| **S4** | MEDIUM (security-relevant) | Overlapping `build()` runs share the fields `_current/_security/_lockHeld`; there is no `ref.mounted` check between `SecurityWiring.open` and `engine.start()`; a stale build can start an engine with the OLD PIN policy and then overwrite or close the live one (`engine_provider.dart:79-161`) | At most one engine is started or left running after a settings change that arrives while a build is in flight; the running one has the NEW `pinGuard.policy.mode`; a superseded build disposes only what it created (engine, wiring, multicast lock) and its port is released. Use a per-build token (or locals + closures), check `ref.mounted` after every await and before `engine.start()`. Test with a fake multicast lock blocked on a `Completer` (see the report's test text) and with the device-id reconciliation case. |
| **S5** | MEDIUM | Mode Fixed with no usable `app-pin` (missing, corrupt, not 6 digits, unreadable): either a RANDOM PIN nobody knows is enforced and shown as if it were the user's, or `build()` fails and the Settings screen is unreachable (`engine_provider.dart:86-101`, `app_shell.dart:23-24`) | **Decision (orchestrator): fall back to Window mode**, never fail the start because of the PIN. In the provider: wrap the read in try/catch, validate `^[0-9]{6}$` after decoding; if invalid or unreadable use `PinPolicy(mode: window)` for this run and expose a non-secret flag (e.g. `pinNeedsReset`). Settings shows "Your saved PIN could not be read. A temporary PIN is shown on the Receive card until you set a new one." and the PIN input. Tests: no `app-pin`; `app-pin` holding `abc` (valid frame); one flipped byte in the `.secret` file; unreadable file (directory in its place). In all four: engine builds, `pinGuard.policy.mode == window`, Settings reachable. |
| **S6** | MEDIUM | Any start failure shows "check that its data folder is writable", including `IdentityLostException` (`app_shell.dart:23-24,109-138`, `l10n_strings.dart:19`) | `IdentityLostException` gets its own message: "This device's security key is missing or damaged. To start fresh, clear the app's data; other devices will then warn that your key changed." No automatic new identity (identity.json bytes unchanged). Log only `error.runtimeType` and the reason name. The in-app "Create new identity" button is deferred (post-MVP). |
| **S9** | LOW but cheap | `unawaited(setDeviceId(...))` inside `build()` can raise an unhandled async error and may call `ref.read` after dispose (`engine_provider.dart:107-111`) | `.catchError` (log runtimeType only) and a `ref.mounted` guard; the engine starts with the stored identity id; no uncaught zone error; engine builds at most twice. |
| **S10** | LOW but same code | `_checkExistingPin` has no try/catch; any stored value counts as "configured"; the Save closure uses `ref` after awaits without `mounted` (`settings_screen.dart:507-519,596-623`) | Unreadable store: no uncaught exception, card shows "not configured"; stored value is validated before "PIN configured" is shown. |
