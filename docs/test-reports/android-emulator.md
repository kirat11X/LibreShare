# Android emulator verification of the prototype APK (agent AE, 2026-11-05)

Status: **both directions work end to end on an Android 15 emulator** (Android -> Linux and Linux -> Android, byte-identical, checksummed). The
APK has real limits that a person will hit on a phone: **transfers die as soon as the app leaves the foreground or the screen turns off**, and
**received files are saved where the Files app cannot see them**. 12 defects are listed at the end, ranked. One was fixed in `android/**`
(keep-screen-on, APKs rebuilt); the rest are Dart (`lib/**`, `packages/**`) and are reported, not edited.

Not verified (cannot be on this box): real Wi-Fi radio, a real phone (OEM battery managers, real NICs), multicast/mDNS discovery between
two devices, notifications, camera/QR scanning, arm64 builds, a Windows peer. The emulator sits behind user-mode NAT; speeds below are
not phone-on-Wi-Fi speeds.

### Emulator quirks on this machine (the first hour went here)
1. **Spaces in the repo path.** `avdmanager create avd` fails with `Could not load devices from ".../Software Engineering LibreShare/..."` and leaves a
   broken AVD. Fix used: write `ls_test.avd/config.ini` by hand (the script does this). The emulator realpath()s itself, so a symlink
   (`/tmp/ls-android-sdk` -> `.toolchain/android-sdk`) is not enough to hide the spaces; it only prints harmless `LD_PRELOAD ... cannot be preloaded` lines.
   `ANDROID_SDK_ROOT=/tmp/ls-android-sdk` is set only inside the commands/script; `tools/env.sh` is untouched.
2. **GPU mode.** `-gpu swiftshader_indirect` (what the task asked for), `-gpu guest` and `-gpu off` all die with SIGSEGV before boot
   (jump through a bad pointer inside `gles_swiftshader/libGLESv2.so`; cores in systemd-coredump). `-gpu swangle_indirect` boots, then dies with SIGILL (`ud2`
   in `libgfxstream_backend.so` `gles2_decoder_context_t::decode`) when the Flutter app first renders. **`-gpu host` works** (NVIDIA Vulkan, headless, no window). The smoke
   script tries `host` then `swangle_indirect` (`LS_EMU_GPU`). Boot to `sys.boot_completed`: 13 to 30 s.
3. Starting the emulator with `nohup ... &` inside one tool call gets it killed when that call ends; run it as its own background job.
4. `adb shell run-as` is unavailable (release APK); app data was inspected through `/storage/emulated/0/Android/data/<pkg>`, `dumpsys`, `ss`.

### How to re-run
```bash
sdkmanager --sdk_root=/tmp/ls-android-sdk "emulator" "system-images;android-35;google_apis;x86_64"   # once, see script header
tools/android_emulator_smoke.sh                       # boots, installs, runs scenario A+B, kills the emulator, exit 0 only if all 18 checks pass
LS_SMOKE_SHOTS=/tmp/shots LS_SMOKE_KEEP_WORK=1 tools/android_emulator_smoke.sh   # keep screenshots and logs
```
Run history of the script on the rebuilt x86_64 APK: run 1 and 2 had 3 failures in scenario B that turned out to be a stale download folder left by an
earlier uninstall (defect 6; the script now removes it). Runs 3, 4, 5 (the last from a freshly created userdata image): **18/18 PASS**, emulator and receiver gone afterwards (`ps` empty, no temp dirs).

## 4. Fix applied in `android/**`

`apps/libreshare_app/android/app/src/main/kotlin/dev/libreshare/libreshare_app/MainActivity.kt`: `onCreate` adds `WindowManager.LayoutParams.FLAG_KEEP_SCREEN_ON`
(verified: `dumpsys window` shows `fl=KEEP_SCREEN_ON`; scenario 3i). It only stops the **screen timeout** from killing a transfer; it does not help when the user presses
power, switches app or answers a call. Trade-off: the screen stays on while LibreShare is the visible app (battery). It is a stop-gap for the foreground-only Increment 2;
the real fix is the Increment 3 dataSync foreground service (or a Dart-driven wake lock only during transfers, then delete the line). Rebuilt with `tools/package_prototype.sh android`.

## 7. Smoke script

`tools/android_emulator_smoke.sh` (self-contained; embeds its uiautomator helper; no hard-coded coordinates: every tap is found by label through `uiautomator dump`). UI automation was reliable across
three consecutive full runs; one run-to-run variable (the stale download folder) was a real product-side defect, not flakiness. Checks (18): host receiver up, emulator boots, APK installs, Home shows, Add-by-IP lookup + add, picker multi-select, send, completion text, host `COMPLETED`, byte-identical, no `.lspart`,
Receive on, app listens on 53318, Incoming dialog, sender `COMPLETED`, "Received 2 files", pulled files identical, no crash. Cleanup: kills the host receiver, `adb forward --remove`, `adb emu kill`, removes its temp dir.
