## Verdict (summary)

**FAIL for the security-critical gate as the code stands.** The wiring core is sound (secure profile, identity persistence, no silent identity regeneration, no downgrade path, no plaintext construction path). But the PIN feature, which is the point of D1, has one BLOCKER (the Settings "Save" shows "PIN configured" before anything is written and swallows write errors: exactly mutation (d) of the card) and two HIGH defects (changing the PIN does not change the running PIN; the sender-side PIN dialog cannot submit a PIN). Fix S1-S3, add the proposed tests, then re-review. Details in section (d).

Counts: BLOCKER 1, HIGH 2, MEDIUM 4, LOW 6.

## (b) Findings

Format: ID, severity, location, what is wrong, concrete scenario, fix (words), proposed FAILING test.

### S1  BLOCKER  "PIN configured" is shown before the PIN is stored; write errors are swallowed
- **Where:** `app:lib/screens/settings_screen.dart:596-623` (Save `onPressed`); display at `630-646`.
- **What:** On Save the handler validates, then immediately `setState(_pinSaved = true; _pinController.clear())` (`604-608`). The real work is an unawaited async closure `() async {...}()` (`613-623`): create dir, `FileSecretStore.put('app-pin', ...)`, then `setPinMode(fixed)`. There is no `try/catch`, no `await` by the caller, no error text. If `put` throws (`SecretStoreException`: chmod refused, disk full, read-only dir, Android/Windows quirks, see S7) the future fails unhandled, `_pinSaved` stays true, the UI keeps showing "PIN configured / PIN is protected", the controller is already cleared, the PIN is gone, and the mode stays whatever it was (typically Off). This is the original D1 defect (a PIN control that only looks active) re-introduced in a rarer path, and it is mutation (d) of the card.
- **Scenario:** support dir on a full disk or with `chmod` unavailable. User picks Fixed, types 6 digits, taps Save, sees "PIN configured". The receiver runs with `PinMode.off`; any stranger on the Wi-Fi can send (consent prompt only). The user believes a PIN protects the device.
- **Fix:** keep `_pinSaved` false and keep the field until `put` has returned; `await` the write inside `try/catch (Object)`; on success then `await setPinMode(fixed)` and only then set `_pinSaved = true` and clear the field; on failure show a visible error ("Could not save the PIN. Nothing was changed.") and leave the previous mode untouched; disable the button while saving; guard every `setState` with `mounted`. Verify success by reading the secret back (`get('app-pin')` equals the entered bytes) before reporting success.
- **Failing test (widget test in `test/d1_pin_persistence_test.dart` style):** setup: `AppHarness` at `/settings`; make `<support>/security` unwritable so `FileSecretStore.put` throws (simplest: create a regular FILE named `security` in the support dir before the app opens settings... if the engine needs that dir pick instead a custom `FileSecretStore` is not injectable, so use `chmod 500` on the security dir after the engine is up, or pre-create `app-pin` slot's `.tmp` as a directory). Action: tap Fixed, enter `654321`, tap Save, `pumpAndSettle` inside `runAsync`. Expected: `find.text('PIN configured')` is `findsNothing`; a visible error text is found; `settingsProvider.pinMode` is unchanged (still `off`); `engine.pinGuard.enforced` is false and the engine was NOT rebuilt (same instance); no unhandled async error reached the zone (`tester.takeException()` is null; wrap in `runZonedGuarded` and assert no error). Twin (positive): same flow on a writable dir shows "PIN configured" only after the stored bytes equal the digits.

### S2  HIGH  Changing the PIN while the mode is already Fixed does not change the PIN in force
- **Where:** `app:lib/providers/settings_provider.dart:58-62` (early return `if (mode == state.pinMode) return;`), `app:lib/providers/engine_provider.dart:62-72` (engine watches only `pinMode`, not the stored PIN), `app:lib/screens/settings_screen.dart:637-644` ("Change" button) and `613-623`.
- **What:** After "Change" + Save with a new PIN the file `app-pin` holds the new PIN, but `setPinMode(fixed)` is a no-op (mode already Fixed), so the engine is not rebuilt. `SecurityWiring.open` read the PIN only at build time (`engine_provider.dart:86-101`), so the running `PinGuard` still has the OLD PIN until the app restarts or something else rebuilds the engine.
- **Scenario:** the user suspects the PIN leaked (a neighbour saw it), changes it, UI says "PIN configured". The old PIN keeps working for senders; the new PIN is rejected with `PIN_INVALID` and counts as a strike for the legitimate sender. Security property "the PIN I set is the PIN enforced" is false.
- **Fix:** make the PIN change a state the engine depends on: e.g. a `pinRevision` counter (non-secret) in settings or a dedicated provider that the engine `watch`es, bumped after a successful write; or have the Save path invalidate `engineProvider` explicitly after the write. Do not put the PIN itself into any provider state that is `toString`-able.
- **Failing test:** setup: harness with Fixed already saved as `111111` and engine running; capture `engine1 = h.engine`, `guard1.currentPin == '111111'`. Action: in Settings tap "Change", enter `222222`, Save, settle. Expected: the engine behind `engineProvider` has `pinGuard.currentPin == '222222'` (or `guard.check(remoteAddress:'127.0.0.9', pin:'111111', exempt:false)` throws `LsErrorCode.pinInvalid` and the same call with `222222` returns normally); stored `app-pin` bytes decode to `222222`. Negative twin: before the fix this assertion fails because `currentPin` is still `111111`.

### S3  HIGH  The sender-side PIN dialog cannot submit a PIN (card behaviour 7 not met)
- **Where:** `app:lib/screens/transfer_screen.dart:129-171` (dialog is a `const TextField(key: Key('pin-field'))` with no `TextEditingController`, no `onSubmitted`, no button); `app:lib/providers/transfers_provider.dart:290-295` (`beginSendTo` without `pin`; there is no retry-with-PIN method); `_drive`/`_finish` only set `pinRequired` (`333`, `548-572`).
- **What:** A receiver that enforces a PIN refuses with `PIN_REQUIRED`; the app marks the transfer failed with `pinRequired: true`, shows the overlay, and the user can type digits that go nowhere. There is no path from the UI to `engine.sendFiles/beginSendTo(..., pin: ...)`. `d1_two_engine_pin_test.dart` passes because it bypasses the UI (`h.engine.sendFiles(..., pin: correctPin)`), and the dialog test only checks that typed text is displayed (`:136-139`).
- **Scenario:** both devices run this app; Bob sets "New each time". Alice can never send to Bob from the app. Fails closed (no bypass), but the PIN feature is unusable end to end, which pushes users to switch the PIN off.
- **Fix:** give the dialog a controller, a Send button (and `onSubmitted`), validate `^[0-9]{6}$`, and call a new `TransfersNotifier.retryWithPin(key, pin)` that starts a new `beginSendTo(device, files, pin: pin)` and clears the old failed view; keep the PIN only in the local controller and the call argument (never in `TransferView`, never in route params or logs); clear and dispose the controller afterwards. Map `LsErrorCode.blocked` to a neutral message too (see S13), without remaining time or attempt counts.
- **Failing test:** widget test with two real engines (as in the existing file): Alice's app harness, Bob with Fixed `381920` on `127.0.0.6`. Action: `startSend` through the notifier, wait for `pinRequired`, pump `TransferScreen`, `enterText(find.byKey('pin-field'), '381920')`, tap the dialog's submit control (key `pin-submit`, to be agreed with the coder), settle. Expected: the files arrive in Bob's download dir, the final `TransferView.phase == completed`, and neither `TransferView.toString()` nor any captured log record contains `381920`. Wrong-PIN twin: enter `000000`, expected text exactly "That PIN was not accepted.", no digit string, no "attempt", no count.

### S4  MEDIUM  Overlapping `build()` calls share single-field state; no `ref.mounted` check between `SecurityWiring.open` and `engine.start()`
- **Where:** `app:lib/providers/engine_provider.dart:79-83` (the only mounted check before the long section), `95-102` (`await SecurityWiring.open`, can take seconds on first run: key generation), `139-149` (`_current`, `_lock`, `engine.start()`), `158-161` (mounted check only after start), fields `52-57`.
- **What:** `ref.onDispose` runs `_closeCurrent()` as soon as settings change. If that happens while build is awaiting at 89 (secret read), 95 (open) or 143 (multicast lock), `_closeCurrent` finds `_security == null` / `_current == null` and closes nothing. The stale build then assigns `_security` (102) and `_current` (139) AFTER the dispose, builds a full engine and calls `engine.start()` (binds a port, announces on mDNS, starts the TLS listener with the OLD PIN policy) and only then notices `!ref.mounted` (158). Meanwhile the next build (which waited only for the already-finished `_closing`) writes the same fields. Because `_current`, `_security`, `_lockHeld` are single fields, the stale build's `_closeCurrent()` at 154/159 can close the NEW build's engine, and a stale engine whose reference was overwritten at 139 is never disposed. The device-id reconciliation (`107-111`) creates exactly this overlap on the one path where the ids differ (it changes a watched setting inside build). Not verified at runtime: depends on Riverpod scheduling and IO timing.
- **Scenario (worst case):** user flips Off to Fixed while the engine is still starting (or reconciliation fires during start). The stale engine (PIN Off) finishes `start()`, and its reference is overwritten by the new engine, so it keeps listening without a PIN while the UI says Fixed; or the live (PIN Fixed) engine is closed by the stale cleanup and Receive silently stops.
- **Fix:** capture a per-build token/generation (or use local variables and closures instead of fields), check `ref.mounted` after every `await` and before constructing/starting the engine, register cleanup for locals created by THIS build (close the wiring you opened if you were superseded), and make `_closeCurrent` take the specific engine/wiring to close. Never share the multicast-lock flags between builds.
- **Failing test:** harness with a fake `multicastLock.acquire()` blocked on a `Completer` (the harness's `PlatformServices.fake()` can be given one). Action: let build reach the lock await, call `settingsProvider.notifier.setPinMode(PinMode.window)` (triggers dispose + second build), then complete the completer. Expected after `pumpEventQueue`: exactly one engine is started in total among all builds that reached `start()` and still running (count via a `bindAddress`-based probe: connect to every port the stale engine could have bound, or wrap with a counting `ReceiveScheduler`/service fake), the running one has `pinGuard.policy.mode == PinMode.window`, no `LibreShareEngine` created by the stale build is left un-disposed, and the stale build's port refuses connections. Second case: pre-create an identity with a different device id than `initialAppSettingsProvider` (forces reconciliation) and assert the same, plus `settingsProvider.deviceId == storedId`, `app_settings.json` has the stored id, and the engine's port is released exactly once.

### S5  MEDIUM  Mode Fixed with no usable stored PIN: silent random PIN, or a start failure the user cannot fix from the UI
- **Where:** `app:lib/providers/engine_provider.dart:86-101`; `core:lib/src/security/pin_guard.dart:43-48`; `core:lib/src/storage/file_secret_store.dart:176-204`; `app:lib/screens/settings_screen.dart:507-519`; `app:lib/screens/app_shell.dart:23-24`.
- **What (answers to suspicion 1):** `PinPolicy(mode: fixed)` + `pin: null` does NOT disable enforcement and does not throw: `PinGuard` generates a random 6-digit PIN (`pin_guard.dart:47`), so the receiver is fail-closed but nobody knows the PIN, and the Receive card shows that random PIN as if it were the user's (`receive_card.dart:44`). Cases: (1) `app-pin` missing, never saved or wiped: `get` returns null (`file_secret_store.dart:182`); (2) file corrupt (checksum/magic): `get` logs and returns null (`192-195`), same as (1); (3) bytes present but not 6 digits or not UTF-8: `utf8.decode` throws `FormatException` (`engine_provider.dart:91`) or `PinGuard` throws `ArgumentError('PIN must be 6 digits')` (`pin_guard.dart:45`), so `build()` fails; (4) file unreadable: `get` throws `SecretStoreException` (`file_secret_store.dart:201`), `build()` fails. For (3)/(4) the whole app shows the generic start-failed page and the Settings screen is unreachable (`app_shell.dart:23-24` replaces the shell), so the user cannot repair or switch the PIN off; Retry repeats the same failure.
- **Scenario:** a damaged `app-pin`, or an old settings file that says Fixed while `security/` was wiped: Receive works but every sender is refused with `PIN_INVALID` (and each wrong attempt is a strike against legitimate users); or the app cannot start at all.
- **Fix:** treat "Fixed but no valid stored PIN" as an explicit state: do not start a guard with a random PIN for Fixed. Either (a) fall back to `PinMode.window` (random PIN, visibly shown on the Receive card) and show a one-time notice "Your saved PIN could not be read; a temporary PIN is used. Set it again in Settings", or (b) fail closed with a message that offers "Reset PIN" (deletes `app-pin`, sets mode Off or Window). Validate (`^[0-9]{6}$` after decoding) in the provider so the error path does not depend on core exceptions, and never let a PIN problem make Settings unreachable.
- **Failing tests:** (i) settings `pinMode=fixed`, no `app-pin` file: build must produce an engine whose `pinGuard.policy.mode` is the documented fallback (window) AND a visible "PIN needs to be set again" indicator in Settings (or fail with the documented message); it must not be `fixed` with an unknown random PIN. (ii) write `app-pin` via `FileSecretStore.put` with bytes `abc` (valid frame, invalid PIN): the engine must not fail with an unhandled error and Settings must stay reachable. (iii) corrupt the frame (flip one byte of the `.secret` file): same expectation.

### S6  MEDIUM  Start failures (IdentityLost, bad PIN, unreadable store) all show "check that its data folder is writable"
- **Where:** `app:lib/screens/app_shell.dart:23-24,109-138`; `app:lib/l10n_strings.dart:19`; error never inspected or logged.
- **What:** Behaviour 3 asks for a clear error. The provider correctly throws `IdentityLostException` (and does not regenerate; checked), but the UI discards the error type and says the folder may not be writable. For `IdentityLostException` (key deleted, e.g. a backup restore or a cleaner) that sends the user in the wrong direction, gives no way to see the cause, and offers only Retry, which can never succeed. The error is not logged either (no diagnostics, which is safe but undebuggable). No secret leaks: `IdentityLostException.toString` prints reason name and at most 16 hex (`credential_store.dart:78-81`).
- **Fix:** map the error type to a dedicated message ("This device's security key is missing or damaged. Other devices will see a changed key if you create a new one.") with an explicit, confirmed "Create new identity" action that calls `SecurityWiring.rotateIdentity` (never automatic), and log only `error.runtimeType` and the reason name.
- **Failing test:** harness whose security dir holds an identity with the private key secret deleted (the existing d1 test already builds this). Action: boot the full app. Expected: finder for `engine-failed` shows text containing "security key" (and not "data folder"), no automatic new identity was created (`identity.json` bytes unchanged), and the log records captured by `installAppLogging(onRecord: ...)` contain no 64-hex run and no PIN.

### S7  MEDIUM  Secret/identity file protection on Android and Windows is unverified and fails hard
- **Where:** `core:lib/src/storage/file_secret_store.dart:12-15,71-74,255-267`.
- **What:** Permissions are set by shelling out to `chmod` (`Process.run('chmod', ...)`); on any failure `put` throws `SecretStoreException('cannot restrict file permissions')` (fail closed, good). On Windows it is a no-op and relies on the profile ACL (documented UNVERIFIED in the file). On Android the previous emulator smoke (18/18) ran the PLAINTEXT app, so `chmod` via `Process.run` and the first identity generation were never exercised on a device. If `chmod` is unavailable or denied, identity creation fails at first start (generic error page, S6) and the PIN cannot be saved (S1). App data is private on Android and `allowBackup="false"` is set (`android/app/src/main/AndroidManifest.xml:35`), so at-rest exposure there is limited to a rooted device. Not verified: any of the above on a device or on Windows.
- **Fix:** none in lib/ necessarily; make D5's manual check explicit: fresh install on the emulator, start the app, assert `files/.../security/` mode 0700 and `*.secret` mode 0600 (`adb shell run-as <pkg> ls -l`), and that Settings Save of a PIN succeeds.
- **Failing test (core-level, owned by the orchestrator's tester):** inject a `ChmodRunner` that returns 1: `FileSecretStore.put` must throw `SecretStoreException` and leave NO `.secret` or `.tmp` file containing the value (already believed covered; re-assert) and the app-level Save must then show the S1 error. Android half: emulator checklist above (not unit-testable).

### S8  LOW  A missing/corrupt `app_settings.json` silently turns the PIN off
- **Where:** `app:lib/services/app_settings_store.dart:102-141` (`loadOrCreate`: damaged JSON, unknown `pinMode` string or missing key all map to `PinMode.off`, new random device id), `143-151` (save).
- **What:** `app-pin` survives in `security/` but the mode lives in the settings file; if that file is lost or damaged the guard is silently not enforced. Writes are atomic (tmp + rename), so corruption is unlikely without outside interference; a same-user attacker who can delete the file can read `app-pin` anyway. The security gain of a fix is small.
- **Fix:** when the settings file is missing or unreadable and `security/` contains an `app-pin`, start with Window mode (visible PIN) and tell the user; or store the mode next to the PIN in the security dir.
- **Failing test:** write `{"deviceId": ...}` without `pinMode` plus a valid `app-pin` in `security/`; load settings; expected: either `pinMode != off` or a recorded "PIN setting was lost" notice. (Debatable; low priority.)

### S9  LOW  `unawaited(setDeviceId(...))` inside `build()`: unhandled error path and a divergence window
- **Where:** `app:lib/providers/engine_provider.dart:107-111`; `app:lib/providers/settings_provider.dart:52-56,71`.
- **What (answers to suspicion 2):** `setDeviceId` sets state synchronously (so the engine, which watches `deviceId`, rebuilds) and then saves. The second build sees `storedDeviceId == settings.deviceId` and does not repeat the call: converges, no loop (provided no one else changes the id; the stored id is read from the identity, which does not change). Teardown of the first engine: `_closeCurrent` disposes the engine and awaits it before `security.close()` (`181-200`), and the next build awaits `_closing` (`82`), so the port is released first, unless the S4 overlap occurs. If the settings write fails (disk full), the returned future completes with an error that nobody handles: an unhandled async error in the zone (crash logging in release, test failure in debug); in-memory settings then hold the new id while the file holds the old one, and the next launch repeats the reconciliation (self-healing). Calling `ref.read(settingsProvider.notifier)` after the provider was disposed would also throw.
- **Fix:** `unawaited(...catchError(...))`, or reconcile once before `LibreShareEngine` construction by reading the identity first (e.g. a tiny provider that opens the wiring and settles the id, then the engine provider depends on it).
- **Failing test:** identity pre-created with id `A`, settings with id `B` and a `AppSettingsStore` whose directory is read-only after load. Expected: the engine starts with `deviceInfo.deviceId == A`, no uncaught zone error (`runZonedGuarded` collector empty), and `engineProvider` builds at most twice (count builds via a probe override).

### S10  LOW  PIN settings card: async hygiene
- **Where:** `app:lib/screens/settings_screen.dart:507-519,596-623`.
- **What:** `_checkExistingPin` has no `try/catch`: an unreadable store throws `SecretStoreException` unhandled from `initState`. It also treats ANY stored value as "PIN configured" without validating the 6 digits (`511-515`). The Save closure calls `ref.read(...)` after awaits without checking `mounted`, which throws if the user left Settings during the write. Positive: the PIN controller is cleared (`607`), disposed (`523-526`), `obscureText: true` (`582`), the PIN is never placed in a `Text`, tooltip, semantics label, `toString` or exception (checked: the `pin` local appears only at `597-603` and `617-618`). Switching to Fixed only persists the mode when `_pinSaved` is already true (`562-568`), and in the Save path the mode is switched AFTER the write (`620-622`), so there is no "Fixed before stored" path (answers suspicion 4; the weakness is S1, not ordering).
- **Fix:** wrap in try/catch, validate the stored value before showing "configured", check `mounted` / `ref.mounted` after each await.

### S11  LOW  Fixed PIN displayed in clear on the Receive card; displayed PIN can go stale after a brute-force rotation; brute-force event ignored

## (c) Checked and found fine (do not redo)

- `SecurityWiring.open` is the only way the app builds security; `security:` is always passed (`engine_provider.dart:137`); no other `LibreShareEngine(` in `lib/` (`grep` = one hit), so no `security: null` path exists.
- Allow-insecure: `allowInsecurePeers` default false in `EngineTuning` (`31`) and nothing in `lib/` sets it; no settings flag, CLI flag, env or debug switch reaches it. Tests override the tuning, release cannot.
- Consent: `autoAccept: false` hard-coded (`engine_provider.dart:123`); `ConsentPolicy()` default (`autoAcceptTrusted: false`) is used by `SecurityWiring.open`.
- Identity is never regenerated by the app: no `rotateIdentity`/`createNewIdentity` call in `lib/`; `IdentityLostException` propagates; core throws before touching files (`security_wiring.dart:45,68-85`).
- Teardown order: engine disposed and awaited, then `trust.close()`, then multicast lock release (`engine_provider.dart:181-209`); `_closeCurrent` is idempotent and each step is guarded.
- Reconciliation converges: after the first correction both ids are equal, `setDeviceId` early-returns on equal ids (`settings_provider.dart:53`).
- Window mode: PIN rotated at every turn-on (`receive_provider.dart:97-99`) and on resume (`123-125`); `choose()` while receiving is an "extend" and keeps the PIN (acceptable); the PIN text is only in the tree under `receiving` (`receive_card.dart:44,75`), absent when Off/Paused/Failed/Starting. The restored mode after an engine rebuild gets a fresh guard, so a fresh PIN.
- PIN validation: exactly `^[0-9]{6}$`, trimmed, rejected before any write (`settings_screen.dart:597-603`; core `pin_guard.dart:30,44`); letters are accepted by the keyboard type but rejected by the regex.
- PIN never in settings JSON (`app_settings_store.dart:60-68`), never in `AppSettings` (no field; `==`/`hashCode` do not include one), no `toString` on `AppSettings` that could leak anything.
- Stored value format: `utf8.encode(pin)` of the validated 6 digits, no newline/padding, framed with magic+length+SHA-256 (`file_secret_store.dart:110-143`), so no trailing-newline comparison failure and a truncated/foreign file reads as "empty", not as a short PIN.
- At rest: `FileSecretStore` writes `<name-hash>.secret`, `chmod 600` applied to the empty tmp file BEFORE bytes are written, directory `700`, flush then atomic rename, failed write deletes the tmp (`file_secret_store.dart:83-108,213-228,247-267`). Android `allowBackup="false"`. Stored in plaintext (same-user readable): the D1 design accepts this for the MVP.
- Both the screen and the engine use the same directory string (`<supportDir>/security`, from `appDirsProvider`), and separate `FileSecretStore` instances only touch different files at the same time (`app-pin` vs `identity.key`).
- Brute-force handling is in core and was already reviewed (5 strikes/IP, 25 global, constant-time compare, identical `PIN_INVALID` message): `pin_guard.dart:96-148`.
- Logging: no `print/debugPrint/Logger/developer.log` of PIN, key or fingerprint in the 7 files; core wiring, guard, key identity and secret store log only fixed phrases and `runtimeType` (`security_wiring.dart`, `pin_guard.dart:11,170`, `key_identity.dart:30-47,132-134`, `file_secret_store.dart:184-202`); `engine_provider.dart` swallows exceptions without logging them. Only 16-hex fingerprints reach the UI/clipboard (`settings_screen.dart:131,142,727`).
- Exception texts are fixed phrases: `ArgumentError('PIN must be 6 digits')`, `IdentityLostException(reason[, fp=<16 hex>])`, `SecretStoreException('secret store is not readable/writable')`: no secret, no stack dump on screen (the shell shows one fixed sentence; no `error.toString()` is displayed).
- Sender wrong-PIN text is the fixed "That PIN was not accepted." (`transfer_screen.dart:28-29`), no attempt count, no PIN length hint beyond the dialog's "6-digit"; `TransferView` carries `pinRequired` (bool) and `refusal` (enum) only, never a PIN (`transfers_provider.dart:129-130,333`).

## (d) Verdict

**FAIL** for the security-critical gate of D1 in its current state.

Reasons: S1 (BLOCKER: "PIN configured" without a real, verified, awaited save; errors swallowed), S2 (HIGH: a changed PIN is not the PIN enforced), S3 (HIGH: the app's own sender cannot enter a PIN, behaviour 7 unmet, and the D1 test hides it by calling the engine directly).

What is good and need not change: engine built with the secure profile, identity persisted and never silently replaced, no downgrade/insecure path reachable from `lib/`, secrets are not logged or shown, at-rest handling of the secret file matches the design (0600/0700, atomic, framed).

Path to PASS WITH FIXES: coder fixes S1-S3; tester adds the proposed failing tests for S1-S5 (S4 and S5 may be accepted as MEDIUM follow-ups only if the orchestrator signs them off in `questions.md`); D5 verifies S7 on the emulator. Then re-review S1-S3 only.

Suggested mutation additions for the second tester (beyond the card's a-h): (i) call `rotate()` only on turn-on and not on resume; (ii) drop `await` before the secret `put` (S1); (iii) remove the `pinMode` early return so a re-save rebuilds (the fix for S2 must turn a named test red when reverted); (iv) swallow `IdentityLostException` in `build()` and catch-return a plaintext engine.
